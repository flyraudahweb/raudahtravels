# Raudah OTA flight suppliers

Start here when adding a flight supplier or changing flight routing. The web and mobile clients use the same OTA API. Supplier credentials and integrations live on the server.

## Current behavior

- `POST /api/ota/flights/search` and `GET /api/ota/places` in [routes/ota.ts](../../artifacts/api-server/src/routes/ota.ts) call the [flight supplier registry](../../artifacts/api-server/src/services/ota/flightSuppliers.ts). The mobile `/api/ota/v1` routes forward to the same handlers.
- The registry runs eligible searches in parallel. A successful result may contain `partialAvailability: true` when another eligible supplier failed. An empty result is valid when no configured supplier covers the route. If there are no configured suppliers, the API returns a configuration error.
- Supplier search is on by default when a matching test or live key is configured. Super admins can pause each supplier under **OTA → Settings → Flight suppliers**. The global flight search switch controls distribution. The online sales switch controls checkout separately.
- The existing Api Provider (Duffel) uses `mode` and `salesEnabled`. Bilalsadasub has independent `bilalMode` (`inherit`, `test`, `live`) and `bilalSalesEnabled` settings. Select Bilalsadasub live while keeping the primary mode at test for the requested mixed-mode rollout. Saved supplier preferences and legacy settings keep their existing behavior.
- Migration `0014_ota_booking_supplier.sql` adds `ota_bookings.supplier`, defaulting old bookings to `duffel`. Apply it before deploying supplier-routing code. Each checkout records both supplier and mode. Supplier callbacks and fulfillment resolve that recorded identity rather than the current search settings. Hotel search and booking use Duffel.
- Bilalsadasub supports one-way nonstop online fares between configured Nigerian airports when its sales switch is on. Other supported results remain estimates. Default coverage is LOS, ABV, KAN and PHC. An encrypted short-lived token preserves the itinerary and quote. Checkout refreshes that exact itinerary and validates passenger ages before payment. The accepted customer price stays fixed once the checkout is saved.
- Web customers can sort and filter estimates alongside online offers. **Check fare** re-runs the domestic search from a short-lived, encrypted fare-check token. It shows the latest estimate for the same offer or a unique matching schedule. An ambiguous result prompts a new search. The **Ask Raudah** action opens a contact form with the flight details filled in. It carries no passenger identity, supplier key or checkout ID.
- **OTA → Fare changes** shows supplier increases found during checks and recorded wallet debits after issuance, separately for sandbox and live. The log records expected and actual costs and links wallet variances by Raudah booking reference. Repeated checks and booking status refreshes deduplicate variance records. Customer payment stays fixed. Earnings use the actual supplier debit once a verified ticket is returned.
- **OTA → Settings → Pricing** has separate flight markups for Api Provider and Bilalsadasub, with 10% defaults and precedence for saved values. The price preview selects the supplier-specific rule. Each payable checkout stores the calculated kobo amount and supplier cost snapshot. **OTA → Earnings** reports confirmed paid bookings, with live and sandbox reported independently. It shows gross earnings against the saved supplier cost before gateway fees and expenses.

## Decide what the supplier can support

Read the provider's current search, pricing, order creation, retrieval, ticket issuance, cancellation, refund and authentication contracts. Confirm whether inventory costs are locked by the offer, or whether a booking request accepts a maximum debit and fails before spending above it. Verify whether prices include taxes and fees, whether they cover everyone in the query, and how pending and issued states are distinguished. Determine what the provider supports for idempotency and lookup after an uncertain order outcome.

For Bilalsadasub, the published booking request takes a `flight_id`, passenger data and a `my_trans_id` for retries. It debits the agency wallet and documents no maximum-price field or guarantee that `flight_id` locks the search fare. Raudah has approved absorbing fare increases for the initial rollout. The default 10% markup is a pricing rule. An increase can exceed it. Pending cancellation can refund the agency wallet, while issued tickets require support. A wallet refund and a customer refund are separate transactions.

## Payment, recovery and delivery

- After canonical Paystack verification, a guarded database claim and its audit event commit atomically. Only the winner dispatches `POST /api/flight/book` with the Raudah booking UUID as `my_trans_id`. Neither workers nor customer refreshes resend a possibly successful supplier POST. Ambiguous outcomes enter review.
- `bilalOrders.ts` handles create, lookup and PDF retrieval. Retrieval uses the recorded provider reference or matches `my_trans_id` from the provider's latest 50 bookings. Pending/ambiguous cases are checked by the maintenance worker and can be refreshed manually. An absent entry in that limited list does not prove no debit occurred. Operators must reconcile older unresolved cases directly with the supplier.
- Confirmation requires a matching transaction ID, route, departure date and cabin, an issued/ticketed state, PNR and enough distinct ticket numbers for the passengers. Pending reservations stay in processing. Payment alone does not confirm a ticket.
- Owner-only `GET /api/ota/bookings/:id/ticket` downloads the supplier PDF only after confirmation. It validates the MIME type, PDF signature, file size and booking state. The supplier key stays on the server. The web UI offers **Download e-ticket (PDF)** when issued.
- Mode-specific Bilalsadasub supplier tokens are encrypted in settings. Paystack can use the shared account key if its mode matches, or hosting-only `BILALSADASUB_PAYSTACK_TEST_SECRET_KEY` and `BILALSADASUB_PAYSTACK_LIVE_SECRET_KEY`. A test supplier checkout needs a test Paystack key even while another supplier is live. Webhooks choose the correct secret from the recorded booking supplier and mode, then verify canonical payment proof in the worker.
- The mobile v1 contract continues to expose domestic estimates without web checkout tokens. The web-specific domestic ticket endpoint and supplier token flow are outside the frozen mobile allowlist. Extend and regenerate that contract when native domestic checkout is introduced.

Provider references are the [Bilalsadasub flight index](https://docs.bilalsadasub.com/llms.txt), [booking contract](https://docs.bilalsadasub.com/reference/flight-book), [booking lookup](https://docs.bilalsadasub.com/reference/flight-booking) and [cancellation contract](https://docs.bilalsadasub.com/reference/flight-cancel). For Travelport, verify the agency's TripServices access group and environment against the [Flights API guide](https://support.travelport.com/webhelp/JSONAPIs/Airv11/Content/Air11/General/AirAPIsGuide.htm) and [ticketing guide](https://support.travelport.com/webhelp/jsonapis/airv11/content/air11/Ticketing/TicketingGuide.htm). Travelport reservation and ticket issuance require separate state handling. Travelport and PKFARE require their own adapters.

## Add a search adapter

1. Add the supplier to `flightSuppliers.ts`. Implement `isEnabled`, `covers`, `search` and `places`. `isEnabled` combines the saved preference and credentials for the active mode. `covers` limits requests to supported airports, journey types, cabins and passengers. Keep supplier-specific transport and schema validation together. Use the provider's fixed HTTPS hosts, a finite request timeout and safe local errors. Prevent redirects from carrying credentials.
2. Add the mode-specific settings in [config.ts](../../artifacts/api-server/src/services/ota/config.ts). Include credentials in `OTA_SECRET_FIELDS` so site settings encrypt them and the admin API masks them. Keep environment fallbacks server-side and use `.env.example` for variable names only. Preserve explicit `false` preferences, old settings rows and optimistic concurrency during saves.
3. Use the pricing helper in [provider.ts](../../artifacts/api-server/src/services/ota/provider.ts) to express customer prices as integer NGN kobo. Preserve supplier currency and the exact amount separately wherever there is a payable quote. Validate airport codes, dates, stop counts and money against the supplier contract. Treat missing or inconsistent itinerary and fare fields as unusable; never invent segments or operating carriers.
4. Return `estimatedFares` for results that require confirmation. Include the normalized display data and estimated kobo amount, with no checkout identifier. The `offers` array is the checkout path. Adding another bookable supplier there requires all the booking changes below.
5. Add management controls in [FlightSupplierSettings.tsx](../../artifacts/raudah-travels/src/components/ota/FlightSupplierSettings.tsx) and enforce the Super Admin check on backend diagnostics. Keep diagnostics read-only unless the action is explicitly labelled as a transaction. Update [apiDocumentation.ts](../../artifacts/api-server/src/services/ota/apiDocumentation.ts) and run `pnpm run docs:ota` when the public contract changes.

## Add a bookable supplier

- Resolve the selected offer to a supplier and credential mode on the server. Persist that identity on the checkout and booking before accepting payment. Scope provider IDs to supplier and mode so equal-looking IDs from different suppliers cannot collide. Preserve servicing of existing rows with a migration and a tested legacy mapping if the booking schema changes.
- Price and verify availability before customer payment. Verify the actual Paystack payment against the server-saved reference, amount, currency, mode and booking metadata. Use a supplier price lock or charge ceiling when supported. For suppliers with an explicitly approved variance policy, preserve the customer-approved amount and record the expected and actual supplier debit with the price variance for reconciliation. Send a changed customer price for review and approval before any additional payment.
- Route reservation, ticketing, lookup, cancellation and reconciliation through the recorded supplier and mode. Use a durable claim and the provider's idempotency key when supported. Once a supplier call can have taken effect, resolve ambiguous retries with lookup or operator review. Search can fall back across suppliers; an ambiguous paid booking must stay with its recorded supplier until reconciled.
- Track reservation, ticket issuance, supplier refund and customer refund independently. Verify callbacks using the provider's documented signing contract, or verify state through the authenticated supplier API. Keep tickets behind booking ownership checks. Leave passenger details, keys and raw provider errors out of public responses and diagnostic logs.
